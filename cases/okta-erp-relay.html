Case study · Automation Engineer, V2X

Letting Okta talk to a legacy ERP it can't reach

A PowerShell Azure Function that sits between Okta Workflows and an IFS ERP on an internal network, relaying a small, allowlisted set of requests in and the ERP's answers back out.

  • PowerShell
  • Azure Functions
  • Azure Government / GCC High
  • Okta Workflows
  • IFS ERP
  • HMAC-SHA256

The problem

Okta had become the system that knows when someone joins, moves or leaves, and identity workflows needed to create, look up and update employee records in the ERP as part of that lifecycle.

The ERP couldn't simply be connected to Okta:

  • It isn't reachable from the internet. It lives on an internal VLAN; Okta Workflows runs as SaaS outside that boundary.
  • It had no API to call. Our version of the ERP had no API layer, so an authorized professional-services partner built one exposing only create, get and update.
  • It's a regulated environment. Everything runs in Azure Government / GCC High, and anything that opens a path inward needs to hold up to review.

The approach

Instead of exposing the ERP, I built a relay: an HTTP-triggered PowerShell Azure Function that is the only thing Okta can reach. The Function App uses VNet integration to reach the ERP on the internal network, so the ERP itself stays unexposed.

Every request passes the same gates, cheapest first, and is rejected at the first one it fails:

  • Authenticate the caller. Okta signs each request with HMAC-SHA256 over a timestamp and the raw body. The relay recomputes it with a shared secret and rejects forged or tampered requests (401).
  • Reject stale and replayed requests. Anti-replay timestamps mean a captured request can't be resent later.
  • Allowlist the operation. Only create, retrieve and update are mapped to ERP calls. Anything else, such as a delete, is refused before the ERP is contacted (403).
  • Normalize the input. Identifiers and values are trimmed and normalized, and only allowlisted fields are forwarded, so an extra field in the payload never reaches the ERP.
  • Handle the upstream honestly. If the ERP is down or errors, Okta gets a clear 502; if the ERP rejects the request, its status is passed back. Successful responses are relayed back so the workflow can act on them.

The result

0inbound paths opened to the ERP
3allowlisted operations: create, retrieve, update
1auditable choke point for every Okta-to-ERP change

Okta Workflows can now keep ERP employee records in step with identity lifecycle events, without the ERP being exposed and without Okta holding broad access to it. Because every request goes through one small function, the rules about what Okta may change live in one readable place.

What I'd tell the next engineer

  • Sign the raw body. Re-serialising JSON changes whitespace and key order and breaks signatures in confusing ways.
  • An allowlist beats a blocklist. New ERP capabilities stay unreachable until someone deliberately adds them.
  • Keep error messages boring. Log the detail; tell the caller only what it needs to retry or stop.
